# 개발 컨벤션

이 문서는 tetris 프로젝트를 함께 개발할 때 지킬 규칙을 정리한 것이다.
규칙을 바꾸고 싶으면 이 문서를 수정하는 PR을 올려 합의한다.

---

## 1. Pull Request 규칙

`main`과 개인 브랜치(`이름/main`)에 직접 push하거나 혼자 바로 merge하지 않는다. 모든 변경은 PR을 거친다.

- 작업 브랜치에서 개발한 뒤 **내 개인 브랜치(`이름/main`)** 로 PR을 올린다. (2번 참고)
- 팀원 **1명 이상이 리뷰하고 승인** 한 뒤에 merge한다.
- PR은 **하나의 기능 또는 하나의 수정**만 담는다. 여러 작업을 한 PR에 섞지 않는다.
- merge하기 전에 **빌드가 성공하는지** 직접 확인한다.
- PR 본문에는 아래 내용을 적는다.
  - 무엇을 했는지
  - 관련 이슈가 있으면 이슈 번호 (`Closes #12` 처럼 쓰면 merge할 때 이슈가 자동으로 닫힌다)
  - 클래스 다이어그램이 바뀌었는지 여부
- merge가 끝난 작업 브랜치는 삭제한다.

## 2. 브랜치 전략

팀원마다 **개인 브랜치**를 하나씩 만들고, 그 아래에서 게임 전체를 개발한다.
모두 완성되면 팀원의 결과물 중 **가장 좋은 개인 브랜치를 `main`에 merge**한다.

작업 브랜치는 내 개인 브랜치에서 만들고, 끝나면 PR을 통해 내 개인 브랜치로 merge한다.

| 브랜치 | 용도 | 이름 규칙 | 예시 |
|---|---|---|---|
| `main` | 팀이 고른 최종 결과물 | - | `main` |
| 개인 브랜치 | 내 작업을 모으는 곳. 항상 빌드되고 실행되는 상태 | `이름/main` | `taeg2/main` |
| `feature` | 새 기능 개발 | `이름/feature/간단한-설명` | `taeg2/feature/board` |
| `fix` | 버그 수정, 리팩터링, 문서 수정 등 수정 작업 | `이름/fix/간단한-설명` | `taeg2/fix/line-clear-bug` |

- 작업 브랜치 이름은 `이름/종류/간단한-설명` 구조로만 짓는다.
- 설명은 영어 소문자로 쓰고, 단어 사이는 `-`로 잇는다.
- `이름`만으로 된 브랜치(예: `taeg2`)는 만들지 않는다. 이 브랜치가 있으면 Git이 `taeg2/...` 브랜치를 만들 수 없다.
- 작업 중 내 개인 브랜치가 바뀌었으면, PR 전에 개인 브랜치를 내 작업 브랜치로 merge해서 충돌을 먼저 해결한다.

## 3. 커밋 메시지

```
<타입>: <무엇을 했는지 한 줄 요약>
```

| 타입 | 의미 |
|---|---|
| `feat` | 새 기능 |
| `fix` | 버그 수정 |
| `refactor` | 동작은 그대로 두고 구조만 개선 |
| `docs` | 문서 (이 문서, 클래스 다이어그램 등) |
| `chore` | 빌드 설정, `.gitignore` 등 기타 |

예시: `feat: Board에 줄 삭제 기능 추가`

- 커밋 하나에는 하나의 변경만 담는다.
- 빌드가 깨지는 상태로 커밋하지 않는다.

## 4. 클래스 다이어그램

클래스 다이어그램은 **모든 개발자가 무엇을 목표로 개발하는지 같은 그림을 보기 위한 도구**다.
처음 설계를 그대로 지키는 것이 목적이 아니므로, 개발하면서 설계가 바뀌어도 문제가 되지 않는다.

- 다이어그램은 draw.io를 사용해 작성하고, Google Drive로 팀원에게 공유한다.
  - [app.diagrams.net](https://app.diagrams.net)에서 저장 위치를 **Google Drive**로 선택해 다이어그램 파일을 만든다.
  - 파일을 팀원 모두에게 **편집자** 권한으로 공유한다. 여러 명이 동시에 열어 함께 수정할 수 있다.
  - 다이어그램 파일 이름: `oop-tetris-class-diagram.drawio` (Google Drive)
  - 다이어그램 링크: (공유 링크를 여기에 붙여 넣는다)
- 다이어그램의 묶음(폴더 모양)은 `tetris/core/` 아래 폴더와 같게 맞춘다. (8번 폴더 구조 참고)
- 개발 순서
  1. 클래스 다이어그램을 먼저 그리고 팀원과 공유한다.
  2. **다른 클래스에 의존하지 않는 클래스부터** 개발하고, 그 클래스를 사용하는 클래스를 나중에 개발한다.
- 개발 중 설계가 바뀌면 **PR을 올릴 때 다이어그램도 같이 수정**하고, PR 본문에 다이어그램에서 무엇이 바뀌었는지 적는다.
  - 다이어그램은 저장소 밖에 있어 PR 리뷰에 자동으로 나타나지 않는다. 리뷰어는 PR 본문을 보고 다이어그램이 코드와 맞는지 확인한다.

## 5. 클래스 작성: OCP와 DIP

목표는 **새로운 종류의 클래스를 추가할 때 기존 코드를 거의 고치지 않는 것**이다.
이를 위해 캡슐화와 추상화를 적극적으로 사용한다.

### OCP (개방-폐쇄 원칙)

확장에는 열려 있고, 수정에는 닫혀 있어야 한다.
새 기능은 기존 클래스를 수정하는 대신 **새 클래스를 추가하는 방식**으로 넣는다.

- 타입마다 `if` / `switch`로 분기하는 코드가 생기면, 추상 클래스와 가상 함수로 바꿀 수 있는지 먼저 검토한다.

### DIP (의존 역전 원칙)

구체 클래스가 아니라 **추상 클래스에 의존**한다.

- 다른 객체를 사용할 때는 추상 클래스의 포인터나 참조로 받는다.
- 구체 클래스를 `new`로 만드는 코드는 **`main`**에 모은다.

### 예시

```cpp
// 추상화: 블록이 해야 하는 일만 정의한다
class Block {
public:
    virtual ~Block() = default;
    virtual void rotate() = 0;
};

// 새 블록 종류는 클래스를 추가하기만 하면 된다 (OCP)
class LineBlock : public Block {
public:
    void rotate() override { /* ... */ }
};

// Board는 구체 블록이 아니라 Block에만 의존한다 (DIP)
class Board {
private:
    std::unique_ptr<Block> current;
public:
    void rotateCurrent() { current->rotate(); }
};
```

새 블록을 추가해도 `Board`는 수정하지 않는다. PR 본문에 **"새 클래스를 추가할 때 기존 코드는 어디를 고쳤는지 (혹은 고치지 않았는지)"** 를 적어서 OCP가 지켜졌는지 확인한다.

### 캡슐화 규칙

- 멤버 변수는 모두 `private`으로 둔다. 외부에서 필요한 것만 멤버 함수로 공개한다.
- 상속을 위한 클래스(기반 클래스)에는 `virtual` 소멸자를 둔다.
- 오버라이드하는 함수에는 `override`를 붙인다.

## 6. 메서드 작성: 쿼리와 커맨드 분리 (CQS)

메서드는 **쿼리** 아니면 **커맨드** 중 하나만 한다. 둘을 동시에 하지 않는다.

| 구분 | 하는 일 | 반환값 | C++ 규칙 |
|---|---|---|---|
| 쿼리 (Query) | 상태를 **읽기만** 한다 | 값을 반환한다 | `const` 멤버 함수로 만든다 |
| 커맨드 (Command) | 상태를 **바꾼다** | 반환하지 않는다 (`void`) | `const`를 붙이지 않는다 |

```cpp
class Board {
public:
    bool isLineFull(int row) const;  // 쿼리: 읽기만 하고 결과를 돌려준다
    void clearLine(int row);         // 커맨드: 상태만 바꾼다
};

// 나쁜 예: 줄을 지우면서(커맨드) 지운 개수까지 돌려준다(쿼리)
int clearFullLinesAndCount();
```

- 쿼리에 `const`를 붙이면, 실수로 상태를 바꾸는 코드를 컴파일러가 막아 준다.

## 7. 코드 스타일

| 대상 | 규칙 | 예시 |
|---|---|---|
| 클래스, 구조체 | PascalCase | `Board`, `LineBlock` |
| 함수, 변수 | camelCase | `clearLine()`, `rowCount` |
| 파일 | 클래스 이름과 같게 | `Board.h`, `Board.cpp` |

- 클래스 하나당 `.h` 파일과 `.cpp` 파일을 하나씩 만든다.
- 헤더 파일 맨 위에 `#pragma once`를 쓴다.

## 8. 빌드 환경

Windows와 Mac에서 모두 빌드할 수 있도록 **CMake**를 사용한다.
빌드 설정은 저장소 루트의 `CMakeLists.txt` 한 곳에서만 관리한다.
Visual Studio 솔루션 파일(`.slnx`, `.vcxproj`)은 만들지 않는다.

### 폴더 구조

```
ku-oop2-tetris/
├── CMakeLists.txt     빌드 설정
├── docs/              문서
└── tetris/
    └── core/          소스 코드 (.cpp, .h)
        ├── main.cpp   구체 클래스를 만드는 곳 (5번 DIP 참고)
        ├── common/    여러 곳에서 쓰는 작은 클래스 (Point 등)
        ├── block/     테트로미노와 블록 생성기
        ├── board/     보드
        ├── play/      한 판 진행 (조작, 낙하, 속도)
        ├── stage/     스테이지, 사진 조각 진행, 앨범
        ├── boss/      보스와 방해 기믹
        ├── medicine/  약 (플레이어 보조 아이템)
        ├── ui/        화면 출력과 키 입력
        └── flow/      게임 루프와 장면 (프롤로그, 앨범 연출, 엔딩)
```

- 소스 파일은 모두 `tetris/core/` 안에 만들고, **하는 일에 맞는 하위 폴더**에 넣는다. 맞는 폴더가 없으면 새 폴더를 만들고, 이 문서와 클래스 다이어그램에도 추가한다.
- `tetris/core/` 아래의 `.cpp`, `.h` 파일은 하위 폴더까지 빌드에 **자동으로 포함**된다. 새 파일이나 새 폴더를 추가해도 `CMakeLists.txt`는 고치지 않는다.
- `#include`는 `tetris/core/`를 기준으로 폴더 이름부터 쓴다.
  ```cpp
  #include "common/Point.h"
  #include "block/Tetromino.h"
  ```

### Windows: Visual Studio

1. Visual Studio Installer에서 **C++를 사용한 데스크톱 개발** 워크로드를 설치한다. (CMake가 함께 설치된다)
2. Visual Studio에서 **파일 → 열기 → 폴더**로 `ku-oop2-tetris` 폴더를 연다.
3. 위쪽 시작 항목에서 `core.exe`를 선택하고 실행한다.

- 솔루션 탐색기에서 새 파일을 만들 때는 **폴더 보기**에서 `tetris/core/` 아래의 알맞은 폴더에 만든다.

### Mac: VS Code

1. 터미널에서 컴파일러와 CMake를 설치한다.
   ```bash
   xcode-select --install
   brew install cmake
   ```
2. VS Code에 **C/C++**, **CMake Tools** 확장을 설치한다.
3. VS Code로 `ku-oop2-tetris` 폴더를 열고, 아래 상태 표시줄에서 **Build**를 누른 뒤 실행한다.

### 터미널에서 직접 빌드 (공통)

```bash
cmake -S . -B build
cmake --build build
```

### OS 차이 주의

Mac에서도 빌드되려면 표준 C++만 사용한다.
아래처럼 Windows에서만 되는 기능은 **입력·화면을 담당하는 클래스 한 곳에만** 모아 두고, 다른 클래스에서는 직접 쓰지 않는다. (5번의 DIP 참고)

| 기능 | Windows 전용 코드 예 |
|---|---|
| 키 입력 | `<conio.h>`의 `_kbhit()`, `_getch()` |
| 커서 이동, 색깔 | `<windows.h>`의 `SetConsoleCursorPosition()` |
| 화면 지우기 | `system("cls")` |
